# push-api-service P1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `push-api-service`: HTTP `POST /v1/push`, `POST /v1/push:batch`, `GET /v1/messages/{msgId}` and gRPC `PushService.SendStream`. One `PushAcceptor` validates, authorizes, rate-limits, dedups, allocates seq, builds the `PushRecord` and produces it to `c1.push.requests`. Consumers keep revocations, tenant policy and message status. The devenv then pushes through the real Push API, and gateway KICKs go through it too.

**Architecture:**
- New Maven module, Spring Boot MVC on virtual threads as the shell only.
- Pure-Java core with small ports (`SeqStore`, `IdemStore`, `RecordProducer`, `MessageStatus`) and Lettuce / Kafka adapters behind them.
- Three ports: public HTTP 8080, gRPC 9443, management 8081 (a second Tomcat connector, as in auth-service).

**Tech Stack:** Java 21, Spring Boot (platform-parent), kafka-clients 3.9.x, Lettuce, grpc-netty-shaded, nimbus-jose-jwt, Testcontainers (Kafka `apache/kafka:3.9.1`, Redis `redis:7.4.2`), platform-contracts-testkit.

**Spec:** `docs/superpowers/specs/2026-11-10-push-api-design.md` (cited "spec §N"). Contracts: `docs/superpowers/specs/2026-11-10-push-contracts-design.md` (cited "contracts §N").

## Global Constraints

- **Module:** `push-api-service`, package `com.pangate.pushapi`, parent `platform-parent` 0.1.0 (`relativePath ../platform-parent/pom.xml`), version 0.1.0. Pom layout and build plugins copied from `push-router-service` (failsafe for `src/it/java` `*IT`, repackage classifier `exec`, Jib image `pangate/push-api-service:dev` with tag `${project.version}`, exposed 8080 9443 8081).
- **Config file name:** `push-api.yml` / `push-api-<profile>.yml`. `PushApiApplication.main` sets `spring.config.name=push-api`.
- **Layering:** classes under `core/` import no Spring and no Lettuce or Kafka types.
- **Defaults (spec §6):** `push-api.cell=c1`; `kafka.produce-timeout=5s`; `kafka.status-group=push-api-status`; `redis.timeout=200ms`; `auth.audience=pangate-api`; `limits` push-rate 1000, push-burst 2000, broadcast-rate 10, status-rate 100; `ttl` default 86400s, max 604800s; `idempotency` ttl 1h, pending-ttl 30s, wait 2s; `seqepochs.refresh=5s`; `grpc.port=9443`, `grpc.max-in-flight-per-stream=1000`; `http` max-body 128KB, max-batch 100, max-batch-body 1MB.
- **Ports by profile:** local HTTP 8085 / gRPC 9443 / management 8084; dev and prod 8080 / 9443 / 8081.
- **Issuer:** local `http://localhost:8090`, dev `http://auth:8090`, prod `https://auth.pangate`. JWKS = issuer + `/.well-known/jwks.json`.
- **Redis keys:** `seq:{p}` (`SeqKeys.seq`), `topicseq:{t}`, `seqepochs`, `runids{seqepochs}`, `idem:{<tenant>}:<key>`, `idem:{<tenant>}:<key>:last`, `msg:{<tenant>}:<msgId>`.
- **Kafka:** records to `c1.push.requests` use `PushKeys.of(r)` keys and `PushHeaders.write` headers (the testkit is a compile dependency here, with `testcontainers` and `junit` excluded, as in gateway-devtools). The producer is idempotent, `acks=all`, zstd, and each send blocks until acked.
- **Logging:** never log payloads or tokens. Log `tenant`, `msg_id`, `kind`, `code`.
- **Errors over HTTP:** `application/problem+json` with `code` from spec §2.4.

## Review Focus

1. Expected: a client retries with the same `Idempotency-Key` after a `503` from a failed produce. Exactly one record reaches Kafka, and it carries the `msgId` and seq first reserved for that key (Task 4, Task 7).
2. Expected: a body whose `tenant` (or `tenantId`) differs from the token's tenant is ignored. The record carries the token's tenant (Task 2, Task 9).
3. Expected: `revoke:c:<client>` blocks only tokens issued before the event. A token that client gets after the event works (Task 5).
4. Expected: a batch mixing valid and invalid items for the same principal returns one result per index. The valid ones reach Kafka in index order (Task 9).
5. Expected: two watchers see one Redis restart (new `run_id`). `seqepochs` is bumped exactly once, and the next seq to a principal carries the new epoch (Task 8).

  - `record Reserved(String msgId, long seq, int seqEpoch, long topicSeq)`; text form `pending|msgId|seq|epoch|topicSeq`.
